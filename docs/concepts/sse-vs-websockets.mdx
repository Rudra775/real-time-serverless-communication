## The Decision

This engine uses **Server-Sent Events (SSE)** instead of WebSockets for client connections. This was a deliberate architectural choice.

## Quick Comparison

| Feature | SSE | WebSockets |
|:--------|:----|:-----------|
| **Direction** | Unidirectional (Server → Client) | Bidirectional |
| **Protocol** | HTTP | WebSocket (upgrade from HTTP) |
| **Reconnection** | Automatic (built into EventSource API) | Manual implementation required |
| **Load Balancing** | Standard HTTP load balancers work | Requires sticky sessions or special config |
| **Firewall Friendly** | Yes (standard HTTP) | Sometimes blocked |
| **Browser Support** | All modern browsers | All modern browsers |
| **Overhead** | Lower (no handshake after initial) | Higher (maintain upgrade) |
| **Use Case** | Real-time notifications, feeds, tickers | Chat, gaming, collaborative editing |

## Why SSE for This Engine?

### 1. Most Real-Time Use Cases are Unidirectional

The majority of real-time features are **server pushing to client**:

<CardGroup cols={2}>
  <Card title="Notifications" icon="bell">
    Server sends, client receives
  </Card>
  <Card title="Live Dashboards" icon="chart-line">
    Server pushes metrics, client displays
  </Card>
  <Card title="Activity Feeds" icon="stream">
    Server broadcasts events, client renders
  </Card>
  <Card title="Stock Tickers" icon="dollar-sign">
    Server publishes prices, client updates UI
  </Card>
</CardGroup>

For these, **WebSocket bidirectionality is overkill**.

### 2. Client → Server is Simple HTTP

When clients need to send data (like acknowledging messages or posting content), they use:
```javascript
// Simple HTTP POST - no WebSocket needed
fetch('/send', {
  method: 'POST',
  body: JSON.stringify({ message: 'Hello' })
});
```

**Benefits:**
- Stateless (can hit any server)
- Standard HTTP tooling works
- Easy to debug with cURL
- No connection state to manage

### 3. Load Balancing is Trivial

**With WebSockets:**
```nginx
# Requires sticky sessions - client must hit same server
upstream websocket {
    ip_hash;  # Sticky session based on IP
    server backend1:8080;
    server backend2:8080;
}
```

**With SSE:**
```nginx
# Any server can handle any request
upstream sse {
    least_conn;  # Route to least busy server
    server backend1:8080;
    server backend2:8080;
}
```

SSE connections can be load-balanced like any HTTP request. This enables true horizontal scaling.

### 4. Automatic Reconnection

**WebSocket:**
```javascript
// You must implement reconnection logic
let ws;

function connect() {
  ws = new WebSocket('ws://localhost:8080');
  
  ws.onclose = () => {
    setTimeout(connect, 1000);  // Retry after 1s
  };
}

connect();
```

**SSE:**
```javascript
// Reconnection is built-in
const eventSource = new EventSource('http://localhost/connect?id=123');
// Browser automatically reconnects on disconnect
```

The browser's `EventSource` API handles reconnection automatically, including exponential backoff.

### 5. Firewall and Proxy Friendly

SSE is just HTTP, so it works through:
- Corporate firewalls
- HTTP proxies
- CDNs (like Cloudflare)
- API Gateways

WebSockets require protocol upgrade, which some proxies block or can't handle.

## When to Use WebSockets Instead

WebSockets are better when you need:

<AccordionGroup>
  <Accordion title="True Bidirectional Communication">
    **Example:** Multiplayer games where clients send frequent updates
```javascript
    // High-frequency client → server messages
    ws.send(JSON.stringify({ x: playerX, y: playerY }));
```
    
    SSE would require separate HTTP POST for each update, adding overhead.
  </Accordion>

  <Accordion title="Binary Data Transfer">
    **Example:** Video streaming, file uploads
    
    WebSockets support binary frames (ArrayBuffer, Blob), while SSE is text-only.
  </Accordion>

  <Accordion title="Sub-Millisecond Latency Requirements">
    **Example:** Trading platforms, real-time collaboration
    
    WebSocket avoids HTTP overhead on every message, shaving microseconds.
  </Accordion>
</AccordionGroup>

## Performance Comparison

### Latency

**SSE (this engine):**
- Initial connection: ~5ms
- Message delivery: ~7ms (P95)
- Reconnection: ~10ms

**WebSocket (typical):**
- Initial handshake: ~3ms
- Message delivery: ~5ms (P95)
- Reconnection: Varies (manual implementation)

<Info>
For most applications, the 2ms difference is negligible compared to network latency.
</Info>

### Throughput

Both SSE and WebSocket can handle:
- 10,000+ concurrent connections per server
- 1,000+ messages/second per connection

**Bottleneck:** Network bandwidth, not protocol choice.

### Resource Usage

**SSE:**
- Lower memory (no upgrade state)
- Simpler server code
- One HTTP connection per client

**WebSocket:**
- Higher memory (maintains upgrade state)
- More complex server code
- One WebSocket connection per client

## Implementation Simplicity

### SSE Server (Go)
```go
func (c *Client) ServeSSE(w http.ResponseWriter, r *http.Request) {
    w.Header().Set("Content-Type", "text/event-stream")
    w.Header().Set("Cache-Control", "no-cache")
    w.Header().Set("Connection", "keep-alive")
    
    for msg := range c.Send {
        fmt.Fprintf(w, "data: %s\n\n", msg)
        w.(http.Flusher).Flush()
    }
}
```

**Total: 8 lines of code.**

### WebSocket Server (Go)
```go
var upgrader = websocket.Upgrader{}

func serveWS(w http.ResponseWriter, r *http.Request) {
    conn, err := upgrader.Upgrade(w, r, nil)
    if err != nil {
        return
    }
    defer conn.Close()
    
    for {
        select {
        case msg := <-client.Send:
            if err := conn.WriteMessage(websocket.TextMessage, msg); err != nil {
                return
            }
        case <-ctx.Done():
            return
        }
    }
}
```

**Total: 20+ lines of code, plus upgrade logic, ping/pong, error handling.**

## Real-World Example

### Notification System with SSE
```javascript
// Client
const eventSource = new EventSource('/connect?id=user_123');

eventSource.onmessage = (event) => {
  const notification = JSON.parse(event.data);
  showNotification(notification.payload.message);
};

// Server (Python backend)
requests.post('http://realtime-engine/send', json={
  'message': 'You have a new message',
  'to_user': 'user_123'
})
```

**Benefits:**
- Client code: 5 lines
- Reconnection: Automatic
- Load balancing: Works out of the box
- Debugging: `curl http://localhost/connect?id=user_123`

### Same System with WebSockets
```javascript
// Client (more complex)
let ws;

function connect() {
  ws = new WebSocket('ws://localhost/ws?id=user_123');
  
  ws.onmessage = (event) => {
    const notification = JSON.parse(event.data);
    showNotification(notification.message);
  };
  
  ws.onclose = () => {
    setTimeout(connect, 1000);  // Manual reconnect
  };
  
  ws.onerror = (error) => {
    console.error('WebSocket error:', error);
  };
}

connect();
```

**Drawbacks:**
- Manual reconnection logic
- Error handling complexity
- Sticky sessions required
- Debugging: Requires WebSocket client tools

## The Hybrid Approach

This engine uses **SSE for downstream** (server → client) and **HTTP POST for upstream** (client → server).
```mermaid
graph LR
    C[Client]
    S[Server]
    
    C -->|POST /send<br/>(HTTP)| S
    S -.->|SSE Stream| C
```

**Best of both worlds:**
- Simple client code
- Stateless upstream
- Automatic reconnection
- Standard load balancing

## Conclusion

For this real-time engine, SSE was chosen because:

<Check>Most use cases are unidirectional (server → client)</Check>
<Check>Simpler implementation and debugging</Check>
<Check>Better load balancing and scaling</Check>
<Check>Automatic reconnection</Check>
<Check>Firewall and proxy friendly</Check>

<Warning>
If you need high-frequency bidirectional communication or binary data, WebSockets are better. For everything else, SSE is simpler and more reliable.
</Warning>
